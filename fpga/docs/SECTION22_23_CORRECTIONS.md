# Corrections and findings for Sections 22-23 of ByteForge_Architecture_v11_draft

Status of each item: **[source]** = read in a primary source; **[inferred]** = my reading of a netlist/image, not confirmed on hardware;
**[choice]** = implementation decision. Nothing here was tested on a physical board.

## A. Contradictions that affect correctness

1. **Display supply (Section 22: "display will use the board's 5 V supply connection" with 3.3 V logic).**
   - Waveshare wiki (https://waveshare.com/wiki/2inch_LCD_Module, fetched 2026-11-07): "Operating voltage: 3.3V/5V", "Please ensure that the power supply voltage and logic voltage are consistent"; the wiki's own wiring tables use **VCC = 3.3 V** for Raspberry Pi, STM32 and VisionFive2 and VCC = 5 V only for the 5 V-logic Arduino UNO; FAQ "maximum power consumption": **3.3V 46mA**. **[source]**
   - Schematic: https://files.waveshare.com/upload/e/ee/2inch_LCD_Module_SchDoc.pdf, **opened in the browser pane and looked at (2026-11-07)**: one sheet with an NPN backlight transistor with two resistors, the panel FPC connector, and two 1x8 headers (VCC GND DIN CLK CS DC RST BL); **no regulator or level-shifter symbol is present**. The file carries no legible revision/title-block text at the resolution I could get, so I cannot cite a schematic revision (the document title shows as "New Output"). The per-net details (VCC to panel supply and LEDA, no series resistors on logic) still come from the earlier text netlist dump and are not re-verified visually. **[visual: structure only; netlist: inferred]**
   - So 5 V supply + 3.3 V logic contradicts the wiki's own "consistent" rule and its examples. **Resolution (hardware plan, revision 2): the module is powered at 3.3 V from a dedicated AP2112K-3.3TRG1 regulator on the carrier PCB, fed from the Tang Nano 5 V header; see docs/HARDWARE_POWER.md.** Section 22's "Tang Nano 5 V header -> Display VCC" row must be replaced by "5 V header -> AP2112K -> 3.3 V -> display VCC".
   - **Tang Nano 3.3 V capacity**: no longer relevant to the display, because the display no longer uses the Tang Nano 3.3 V rail (the earlier analysis of the ME6211C33 rail is superseded). **[plan change]**
2. **Orientation in Waveshare's reference code.** `LCD_2IN_SetAttributes(HORIZONTAL)` sends MADCTL 0x36=0x70, then `LCD_2IN_InitReg()` sends 0x36=0x00 again, so the final MADCTL is 0x00 (portrait) while the software uses 320 wide x 240 high windows (CASET 0..319, RASET 0..239). **[source: waveshare/Pico_code @ c50bc57, c/lib/LCD/LCD_2in.c, sha256 700cbd15...4533]**
   The demo replays the reference init stream exactly (including 0x36=0x00) and uses the window CASET 0..239 / RASET 0..319 that is consistent with 0x00. Whether the reference's horizontal mode ever displayed correctly is not established; **orientation must be judged on the real panel**.
3. **Pins shared with the RGB LCD connector.** Pins 25-31 (buttons, reset), 42 (BL) and 77 (DC) are also nets of the 40-pin RGB connector (LCD_HS, LCD_VS, B7..B3, R3, CLK). **[source: Sipeed pin-label image]** The 40-pin FPC connector must stay unplugged (Section 22 already says so; this confirms it is necessary).

## B. Section 22 pin assignment - checked against the Sipeed schematic net labels (revision 2: CS -> pin 41, RST -> pin 48)

**Revision 2 remap:** `lcd_cs` 75 -> **41** (IOB43A, bank 4, net `PIN41_LCD_R4`), `lcd_rst` 86 -> **48** (IOR49B, bank 3, net `PIN48_LCD_DE`). Both new pins are RGB-LCD-connector nets (text of the Rev 1.30 schematic copy), so the RGB connector must stay disconnected, as must HDMI. Bank 3 is 3.3 V in Sipeed's legend; **bank 4 (also pin 41, like pin 42) is still not confirmed**. The remap removes the HSPI-labelled pins 75 and 86 from the display; **pins 73 (DIN) and 74 (CLK) still carry `PIN73_HSPI_DIN2` / `PIN74_HSPI_DIN3`**, so the BL616-contention risk below remains open for those two. The paragraph below describes the pre-remap state.


Pin functions/banks from Apycula 0.35 (GW2AR-18C, QN88): 73 IOT40A b1, 74 IOT34B b1, 75 IOT34A b1, 77 IOT30A b1, 86 IOT4A b0, 42 IOB42B b4, 25-31 IOB6A..IOB18A b5, clock pin 4 IOL7A b7. Net labels read from the text of Sipeed's schematic (Tang_Nano_20K_3921_Schematics.pdf, Rev 1.30, 2023-07-11; the official dl.sipeed.com file listing refused my fetch, so this is a distributor-hosted copy of the same document): **[source, text only]**
- 25 `PIN25_LCD_HS`, 26 `PIN26_LCD_VS`, 27 `PIN27_LCD_B7`, 28 `PIN28_LCD_B6`, 29 `PIN29_LCD_B5`, 30 `PIN30_LCD_B4`, 31 `PIN31_LCD_B3`, 42 `PIN42_LCD_R3`, 77 `PIN77_LCD_CK` - all RGB-LCD-connector nets, so the 40-pin FPC connector must stay unplugged. (Earlier docs called pin 77's net "LCD_CLK"; the schematic label is `LCD_CK`.)
- **Correction to my earlier statement**: I had written that 73/74/75/86 are "plain header pins (no shared net)". The schematic text instead lists **`PIN73_HSPI_DIN2` + `PIN73_SYS_LED3`, `PIN74_HSPI_DIN3` + `PIN74_SYS_LED2`, `PIN75_HSPI_DIR` + `PIN75_SYS_LED1`, `PIN86_HSPI_CSN`** (and `PIN76_HSPI_DAT`). These are names of nets that go to the on-board BL616 USB/JTAG MCU ("HSPI"). The extraction does not prove a direct wire to the BL616, and I do not know whether the BL616's firmware ever drives them, so **possible contention on LCD DIN/CLK/CS/RST (pins 73/74/75/86) is an open risk**. Revision 3920's change note reads "Changed pin assignment of BL616". Mitigation to check on the board (continuity from FPGA pin 73/74/75/86 to the BL616 pins, or reading the schematic page visually at high zoom, which I could not do) or move the display to pins with no HSPI/LED label. I did not change the assignment because the evidence is net names only. **[open, important]**
- Pin 30: Apycula says IOB14B; the schematic pin table text shows "IOR14B" for pin 30. I treat that as an extraction/typing difference; unresolved (it only matters for bank/voltage, bank 5 is 3.3 V in Sipeed's legend).
- **Pin 42 (and now pin 41) / bank 4 voltage - NOT conclusively resolved.** Sipeed's pin image legend omits bank 4. The schematic text places "VCCO_4 +3V3" together (VCCO_4 = FPGA pin 44), in both the Rev 1.30 and Rev 1.22 copies, but the same extraction put "+1V0" beside VCCO_5 (bank 5 is 3.3 V per Sipeed's legend and examples), so text adjacency is not reliable. I opened the schematic in the browser pane but its resolution (800x600, PDF zoom controls not operable) was too low to read net names on the FPGA sheet. Working assumption: bank 4 = 3.3 V (supported by Sipeed's own LCD example driving pin 42 as LVCMOS33). Impact is small for this design: BL goes through a 1 kOhm resistor to an NPN base, so even a lower VCCO_4 would still switch it; only the IO_TYPE declaration could be wrong. **[open]**
- No assignment was changed. Oscillator: 27 MHz on pin 4 (`PIN04_SYS_CLK`; Sipeed example constraint). **[source]**

## C. Backlight drive

BL goes through R2 = 1 kOhm to an NPN base with R3 = 10 kOhm to ground (R1 = 10 Ohm in the LEDK path). A 3.3 V GPIO is adequate and the GPIO does not source LED current. **[inferred from netlist]** The CST sets BL to PULL_MODE=DOWN so the backlight stays off while the FPGA is unconfigured/configuring (the pin state during configuration was not verified).

## D. Display timing and initialization

- **Panel reset**: after system reset, RST high 100 ms, low 100 ms, high 100 ms (RST held low while the system is in reset). Source: Waveshare reference `LCD_2IN_Reset()` (not the ST7789 datasheet, which I did not check). All three phases are derived from CLK_HZ (2 700 000 clocks each at 27 MHz). **[source: Waveshare code]**
- **Init sequence**: 71 bytes / 19 commands, extracted mechanically from `LCD_2IN_InitReg()` by `sw/extract_reference_init.py` into `tb/ref_init.hex`; the testbench compares what the demo sends against that file. No panel offsets are used by the reference (raw coordinates). **[source]**
- **Added delay (deviation from the reference)**: the reference has no delay between SLPOUT (0x11) and DISPON (0x29). Sitronix **ST7789V datasheet v1.6, section 9.1.12 "SLPOUT (11h)", Restriction row** (read from the PDF at https://wiki.pine64.org/images/5/54/ST7789V_v1.6.pdf, viewed on screen, PDF page ~183-184 of 316): "It will be necessary to wait 5msec before sending any new commands to a display module following this command to allow time for the supply voltages and clock circuits to stabilize. It will be necessary to wait 120msec after sending sleep out command (when in sleep in mode) before sending a sleep in command." **[source]** So the datasheet requires **>= 5 ms** before the next command; the **120 ms is the wait before a SLEEP IN command, not before DISPON**. My earlier text ("120 ms after SLPOUT") was wrong. The demo waits 125 ms, which is conservative and satisfies the 5 ms rule with large margin; it is not a datasheet requirement, and the Waveshare reference (no delay) would violate the 5 ms rule on paper. Whether the Waveshare panel's controller is exactly an ST7789V (the wiki names ST7789V) was taken from the wiki. The demo's `tb_demo` still checks for >= 120 ms-equivalent; that is the design's own choice. Keeping 125 ms is a decision for you: 10 ms would also satisfy the datasheet.
- **Hardware reset timing**: the datasheet's Reset Timing section (7.4.5) was **not read** (could not navigate to it with the available viewer), so the 100/100/100 ms phases remain Waveshare-reference values only. **[open]**
- **SPI clock**: SCLK = 27 MHz / (2 x SPI_HALF_CLKS) = 6.75 MHz (half = 2). The Waveshare reference runs 10 MHz; the wiki states no maximum. 6.75 MHz is therefore below the reference rate, not a datasheet-proven limit. **[choice]**

## E. Buttons and reset

- Section 22 specifies external 10 kOhm pull-ups. The CST additionally enables the FPGA's internal pull-up on those pins so the design is safe without the external resistors; with both present the pull-up is simply stronger. **[choice]**
- Reset-button pin (31) is a separate input to the reset conditioner; panel reset is generated separately by the display controller (as Section 22 requires).
- Startup mechanism actually used: Gowin registers power up from their `initial` value after configuration. `reset_conditioner` declares `chain = 2'b11`/POR flag initial values and additionally holds reset for 256 clocks (`POR_CYCLES`) after configuration. Whether the Gowin tools honour these initial values was seen only in the open-source flow, not in the Gowin IDE. **[open]**

## F. Memory-map / bus clarifications (Section 23 left these open)

- Every bus transaction takes at least 2 clock edges (capture, then completion) plus any stall, and requires `data_request` to go low between transactions. Unmapped reads return 0; unmapped and read-only writes complete without effect; the bus decodes the full 16-bit address (e.g. 0xFF10 is not aliased by 0x0010).
- The ROM returns HALT (0x8800) for any address >= 0x2000 (no truncation) and for unwritten words.
- The delay starts at the capture edge and the bus completes after exactly value x CLKS_PER_MS clocks (+2).
